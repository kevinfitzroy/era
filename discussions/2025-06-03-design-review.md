# 场景拆解：方案评审

> 2025-06-03，核心洞察：不同角色的 Agent 必须从不同角度提问

## 基本流程

```
技术 Agent 出方案（PR 形式）
        │
        ▼
各方 Agent 按自己角色的视角评审
        │
        ├── 业务 Agent：这方案解决我的问题了吗？我理解吗？
        ├── 技术 Agent（同行）：架构合理吗？有坑吗？
        └── 其他角色（按需）
        │
        ▼
意见汇总 → 一致 → merge / 分歧大 → 人工介入
```

## 核心设计：角色化评审 Prompt

不是千篇一律的"请评审这个方案"——**不同角色的 Agent 从不同角度切入**。

### 业务 Agent 的评审视角

```yaml
role: business
review_lens:
  - 这个方案解决了我最初提的那个问题吗？
  - 方案描述的业务流程我能看懂吗？哪里看不懂？
  - 时间安排是否可接受？
  - 有没有隐含的体验变化我需要知道的？
  - 如果方案做了取舍，取舍的是什么？会影响谁？
```

Agent 读完方案后，用自然语言回放给业务人：
> "技术侧提的方案是这样的：他们打算……预计需要 3 天。我觉得有两个点你需要注意：第一，……；第二，……。整体上我觉得能解决你之前说的报表慢的问题。你觉得呢？"

### 技术 Agent 的评审视角

```yaml
role: tech
review_lens:
  - 架构是否合理？有没有过度设计或设计不足？
  - 有没有性能/安全/兼容性的坑？
  - 是否引入了不必要的依赖？
  - 有没有更简单的方法达到同样效果？
  - 测试策略够不够？
```

### QA 角色的评审视角（后续扩展）

```yaml
role: qa
review_lens:
  - 边缘情况考虑了吗？
  - 回归风险在哪？
  - 需要什么样的测试覆盖？
```

## 模板结构

方案评审的 YAML 模板不同于提需求——它是**多视角评审判据**，不是一个填空表单：

```yaml
type: design_review
pr_url: "..."

# 方案摘要（技术 Agent 生成，给其他 Agent 看）
summary: "..."

# 评审维度（按角色激活不同 section）
review_sections:
  business:
    questions:
      - "方案描述的业务流程你能理解吗？"
      - "时间/成本是否可接受？"
      - "有没有影响你日常使用的变更？"
  tech:
    questions:
      - "架构合理吗？"
      - "有没有技术债务风险？"
      - "是否有更简单的替代方案？"
```

每个 Agent 只用自己角色的 section。同一个方案，不同 Agent 看到不同的"评审清单"。
