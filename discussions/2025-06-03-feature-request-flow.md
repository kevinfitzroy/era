# 场景拆解：提需求（Feature Request）

> 草稿 v0.1 — 待用户反馈后迭代

## 角色

- **需求方**（业务侧的人 + 他的 Agent）
- **实现方**（技术侧的人 + 他的 Agent）

## 流程（5 步）

### 第 1 步：捕捉 — Agent 引导需求方说清楚

Agent 主动问，不等需求方自己组织：

```
Agent: "你想解决什么问题？现在哪里不方便？"
      ↓
人回答（可能很模糊："就是那个报表太慢了"）
      ↓
Agent: "哪个报表？慢到什么程度让你觉得没法用？有没有具体场景？"
      ↓
人补充
      ↓
Agent: "如果这个问题解决了，你期望的理想状态是什么样的？"
      ↓
人描述期望
```

**原则**：Agent 不问"你要什么功能"（那是设计问题），而是问"什么痛点、什么期望"。

### 第 2 步：结构化 — Agent 内部整理

Agent 把对话整理成统一格式，例如：

```yaml
type: feature_request
id: FR-20250603-001
title: "报表查询加速"
problem:
  - 用户打开月度汇总报表时等待超过 10 秒
  - 影响：财务团队每月初集中查报表，体验很差
expectation:
  - 查询结果在 3 秒内返回
context:
  - 涉及的报表：月度营收汇总、部门费用明细
  - 使用高峰：每月 1-5 号
unknowns:
  - 数据量多大？（待确认）
  - 是否所有报表都有这个问题？（待确认）
```

### 第 3 步：确认 — 需求方 sign-off

Agent 把结构化内容用**自然语言**回放给人：

> "我帮你整理一下：你遇到的痛点是月度汇总报表打开超过 10 秒，财务团队每月初集中使用的时候特别难受。你期望能降到 3 秒以内。涉及营收汇总和部门费用两张表。目前有两个信息还没确认：数据量多大，是否所有报表都这样。你看我理解得对不对？有没有遗漏？"

人确认 / 补充 / 修正。**这是人唯一必须做的事。**

### 第 4 步：交付 — Agent ↔ Agent 握手

业务 Agent → 技术 Agent：发送结构化需求。

技术 Agent 的职责：
- 做初步可行性判断（能做 / 做不了 / 需要更多信息）
- 如果需要更多信息，**回问业务 Agent**（不是直接找人）
- 如果可行，给大致方案方向和时间量级

### 第 5 步：跟踪 — 双方可见

需求进入一个简单的状态流：

```
已提交 → 评审中 → 已排期 → 开发中 → 已完成 → 已验收
                ↓
              需澄清（回到第 1 步）
                ↓
              暂不处理（记录原因）
```

## 这个设计的几个意图

1. **需求方不需要知道怎么写需求文档** — Agent 引导对话就够了
2. **结构化输出统一了 Agent ↔ Agent 的"语言"** — 技术 Agent 收到的始终是同一格式
3. **人在关键节点签字** — 第 3 步确认，最后验收
4. **信息缺口被显式标注**（`unknowns`）— 不假装完整
