# challenges/ — ERA 对自己的常设对抗

> 这里存放对 **ERA 方法论本身** 的对抗性挑战 —— 不是对某个方案,是对这套框架
> "会不会立不起来 / 会不会一开始就想错了"的攻击。
> 每条挑战**永久留存**,即使已被回应、被驳回、或被接受为"已知局限"。**这里不 close 任何东西。**

## 为什么是文件夹,不是 issue / PR

- **issue 会被 close** → 一旦"解决"就从默认视图消失。但未采纳 / 部分解决 / 被驳回的挑战
  **恰恰最该留着**——它们是方法论的已知弱点清单。
- **PR 会 merge / 改写** → 内容不稳定,挑战原文会被后续提交盖掉。
- **文件夹 = append-only**:可 diff、永远在仓库树里可见、git 留痕。一条挑战被回应后**不删除**,
  只在末尾追加「回应」段。

这本身就是 issue #3
(同模型 agent 易达成虚假共识)的解药:把"有人真的反对过"做成**不可被静默关闭**的常驻记录。

## 它和 `red_team` lens 什么关系

| | 靶子 | 在哪 |
|---|---|---|
| `era/templates/design_review.yaml` 的 `red_team` lens | 单个**方案**(对象级) | 正常 workflow 内,PR 评审时 |
| `challenges/`(本目录) | **方法论本身**(元级) | 方法论维护,跨越任何具体方案 |

同一种对抗精神,高一层靶子。

> ⚠️ **术语统一**:本仓库一律用 **`red_team` = 攻方 / 挑战者**(security 界惯例)。
> 日常口语可能把这个角色叫"蓝军 / 蓝队"(PLA OPFOR 那套约定,蓝 = 攻方)——**指的是同一个角色**。
> 仓库里只认一套颜色,别让红、蓝两种相反约定在文档里打架。

## 一条挑战长什么样

每条挑战一个文件:`NNNN-短标题.md`(编号零填充,方便排序),带一个**只增不删**的状态:

- `open` —— 提出了,还没处理。
- `partially-addressed` —— 部分回应(链 commit / PR),仍有残留。
- `addressed` —— 已回应(链改动);**文件保留**,记录"曾经这是个问题、怎么解的"。
- `rejected` —— 评估后认为不成立(写清理由)。
- `accepted-wontfix` —— 成立,但接受为已知局限、暂不改(写清为什么可接受)。

回应是**追加**的:在原挑战末尾加「## 回应」段,链到 commit / PR,**不改原文**。

## 怎么用(把对抗固化下来)

1. **每次重大改动 / 每轮真实试跑后**,强制跑一遍"挑战自己"(像 `0001` 那样:默认假设方法论
   有问题,去找它)。至少产出一条新挑战,或确认某条旧挑战已解。
2. 这把 fidelity 的"主动暴露失真"从**个人层面**(单个 agent 对自己的人保真)提到了**方法论层面**
   (方法论也得对自己保真,不许自我感觉良好)。
3. 与 #11 真实试跑
   联动:试跑暴露的"方法论本身的问题"沉淀到这里;这里 `open` 的挑战 = 试跑要重点验证的假设。
