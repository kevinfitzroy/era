# 0001 — 整套机制太重、且无人执行,可能立不起来

- **日期**:2026-06-04
- **挑战者**:对谈 agent(实施视角对抗 / 蓝队)
- **靶子**:ERA 方法论整体 —— 可实施性
- **状态**:`open`
- **触发**:从"实施视角、不带历史"重看全仓后提出。

## 一句话

单看每个机制都合理;合在一起,对一个 v0.1、零真实用户的项目**过重了**。
风险不在某一条错,而在于**整套立不起来、也没人在执行**。

## 四条风险(按严重度)

### 风险一(最致命):没有任何东西在"执行"这套方法论

provenance、sign-off、fidelity、representability —— 全是 `.md` / `.yaml` 里的**指令**。
没有 linter、没有 CI gate、没有 bot 拦截。它 100% 靠 agent 每一轮自觉读 `CLAUDE.md` 并照做。
**LLM 会漂移**:长会话里它会悄悄不再每个字段标 `source`、不再诚实自评 representability。

→ 真要落地,**至少挑一件事变成机器可校验**(比如一个 issue bot:正文缺 `source:` 标注就打回)。
否则方法论是蒸汽,看着严谨,跑起来就化了。

### 风险二:标注税可能把 ERA 本想消除的摩擦又请回来

ERA 的卖点是"人不用学沟通,agent 扛"。但现在每个需求都要:逐字段 `source` + `representability`
+ 差异 sign-off + `human_said` + fidelity 计数。**对人来说,sign-off 那一步每次还是要逐条审
inferred / unconfirmed**——而且要在 **AR 眼镜 + 语音**这个最不适合审结构化 diff 的界面上做。
逼出"差异驱动 sign-off"的那个约束(AR / 语音),恰恰也让 sign-off 本身很痛。

### 风险三:最核心的两个机制,押在 LLM 最不可靠的能力上

`representability=low` 弃权、fidelity 自评 —— 都要求 agent **知道自己不知道**(校准的元认知)。
同模型 agent 系统性地**过度自信**,这恰恰是它最差的能力。corrected 率还算扎实(是真实数据),
但 inferred 占比、representability 是自报的,既不可靠也可被表演。
**"amplifier not proxy" 最吃劲的支点,踩在最软的地基上。**

### 风险四:per-person 常驻 host,线性且重 → 冷启动门槛劝退

N 个人要 N 台常驻 host + Maestro + agent + AR + 语音,**先把整个机队立起来才有任何价值**。
多数团队不会。而"每人一台常驻 host"其实**不是 amplifier 的核心**——它是个可砍的采纳杀手。

## 建议:画一条 MVP 线,其余降级为"疼了再开"

好消息是——**便宜、高价值的部分,恰好就该是 MVP;贵的,恰好都可缓。**

| 留进 MVP(便宜且高杠杆) | 缓到"疼了再开"(贵或没数据) |
|---|---|
| 共享 repo + issue/PR 模板带 **`source` 标注** | fidelity 度量(**零真实数据,阈值 ~1/3 是凭空定的**) |
| **一步**人工 sign-off | representability 自评分(不可靠,等校准) |
| 人直连永远放行(几乎零成本) | red_team 设为可选,别强制 |
| 挑 `source` 标注做**一个**机器校验,证明可执行路径 | 流程推进权形式化、scribe 授权子协议 |

核心判断:**ERA 现在是"在第一笔交易发生前,先写好了整套监管框架"。**
它的失效模式还没观察到,却已经为想象中的失效模式建了一堆机制——很可能在解不会出现的问题,
同时漏掉真会出现的。

## 与 #11 的关系

"会不会太复杂"这个问题,只有让真实团队跑**最小版**才答得出。所以先砍到最小,跑起来,
让疼痛告诉你该加回哪一条。
本挑战是 #11 真实试跑
的**前置**:先定最小可跑集,再谈试跑。
